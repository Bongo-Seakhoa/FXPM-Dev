Orientation

One command, one honest book

FxPM searches 100 currency-pair and CFD symbols across six timeframes and four market regimes — 2,400 possible strategy slots — and publishes a validated “winner book” that the execution loop trades. The rebuild documented here changes one thing everywhere: every number that reaches a trading decision must be derived from raw evidence and re-verifiable from bytes — never declared, never assumed, never quietly relabeled.

The operator workflow, end state

  1. Run the optimizer

    python pm_main.py --optimize — a multi-day unattended run that executes the complete evidence chain and publishes a validated book, or stops with a typed reason.

  2. Read the evidence pack

    Causal PASS/FAIL, the book's contents, capital calibration receipts, per-cell outcomes. This step is yours: the system explains itself but doesn't decide for you.

  3. Paper-trade the book

    --trade --paper executes the book with real orders on the verified demo account. Forward outcomes accumulate against the validation predictions.

  4. Deliberate go/no-go

    Comparing probation evidence to validation expectations is a human decision, always.

  5. Go live

    --trade, inside an externally signed capital envelope, with expiry forcing periodic re-validation through the same full chain.

Orientation

Architecture, before & after

The old system was one pipeline that computed results and wrote them down. The new system is a chain of small, single-purpose authorities, where each layer produces sealed evidence and the next layer re-verifies it from raw bytes before using it.

The old shape

Before — one trusted pipeline

One large optimizer loop per symbol: load data → compute indicators → grid-search → score → write the winner into a config file. Results were trusted because the code that produced them was trusted. If any step was wrong — a leaky validation window, a missing cost, a silently skipped failure — nothing downstream could tell. Publication was a file write; a crash could corrupt the live book.

After — a chain of verifying authorities

Each stage is a separate module with one job, producing content-addressed artifacts (files named by the hash of their bytes). The consumer of each artifact independently re-derives and re-checks it. The practical purpose is reproducibility and accidental-drift detection: the reviewed calculation, data and deployed model must be the same bytes.

Why the dependencies only point forward

The historical books are evidence, never deployment candidates. Their unseen outcomes can approve or reject the frozen discovery/refit process, but they cannot directly nominate today's parameters. The current-search authorization is allowed to exist only after an independently reverified causal PASS and is hash-bound to that decision. The only book eligible to move toward demo is the separately produced latest-cutoff current book.

Three structural differences that matter most

Commitment before evidence

In the old system, the search space was whatever the loop happened to iterate. Now the planner freezes the entire strategy/parameter domain, the exact 128 designs that will actually be tried, the timeframe depth ladders and geometry-only depth rule, and the anchor calendar into sealed plans before the first backtest. Multiplicity accounting (how many things were actually tried, which determines how skeptical to be of the winner) becomes a mechanical fact instead of an estimate.

Two agents, independent correctness review

Two AI agents (Claude and Codex) build in separately claimed lanes on a hash-chained coordination ledger. Every change freezes to exact byte hashes; the other agent checks chronology, statistical gates, genuine-evidence construction, cost realism, model parity, bounded execution and failure behavior on those same bytes. The producer of a component is not the only reviewer of it.

Failure is a first-class output

The old pipeline had two outcomes: a winner, or nothing. The new book records a typed disposition per cell (see Integrity principles), so “no result” always carries why — no data, no regime occurrences, not enough statistical power, or an infrastructure fault that aborts the run rather than being written down as a market opinion.

The data pipeline — from broker tick to sealed dataset

Everything downstream is only as honest as the data. This page follows market history from the MT5 terminal to the frozen, content-addressed datasets the search actually runs on — including how much data that is, and what cleaning and validation happens where.

How much data is frozen

Each of the six timeframes is acquired independently and natively — D1 bars come from the broker as D1 bars, never resampled from M5. The source-history contract (fxpm-timeframe-evidence-v3) fixes a bounded calendar envelope per timeframe. Its persisted segment names are still optimizer_train, tuning_validation, and final_lockbox, but those names do not describe the new experiment. The production experiment is formed later from repeated as-of anchors, rolling inner folds, and unseen outer periods.

Do not infer a stale lockbox deployment

The source envelope is inventory, not a command to train once at its beginning and deploy a parameter vector from its end. Historical anchors take causal prefixes from this inventory. After the historical process passes, the entire search is rerun through the latest fully closed common cutoff.

The pipeline, step by step

  1. Acquisition tools/acquire_native_history.py · MT5 API

    Bars are pulled per symbol × timeframe from the terminal connected to the live-data account (FBS-Real). Each pull records the account identity, server, and terminal state into provenance — a per-cell identity check aborts if the account changes mid-run (this caught a real incident where demo data would otherwise have contaminated the store).

    in broker history via MT5  →  out per-cell CSV leaf + provenance receipt
  2. Validation at write time acquisition contract v5 / authenticity v4

    Before a leaf commits: schema and column checks, strictly increasing UTC timestamps, duplicate-bar rejection, OHLC sanity (high ≥ low, open/close inside range), spread column presence, declared-versus-observed count consistency, and gap classification. Authenticity, provenance, an empty advertised source, or a declaration mismatch are blocking. Calendar reach, fixed row targets, and the ≈95% session-coverage estimate are diagnostics: they may later produce typed insufficient evidence, but cannot erase genuine observations or become a market verdict. Expected closures are classified, never synthetically filled.

    reject ⇒ typed quarantine (mixed-source · corrupt · empty or declaration-mismatched) — never silently repaired
  3. Activation pm_native_activation · data/native/ACTIVE.json

    A validated acquisition run is activated: every available file and every legitimate terminal-unavailable record is hashed into one 100 × 6 roster and ACTIVE points at that identity. Consumers refuse bytes that do not match the activation manifest. A technical or provenance failure is not an unavailable market cell; it blocks the generation.

    out activation manifest — the single source-of-truth ID every downstream receipt references
  4. Sealed cutoff prefixes pm_native_prefix_production

    The engine never touches raw files. For each search (historical anchor or current), the activated dataset is trimmed causally at an exact cutoff timestamp — only bars whose close is at or before the cutoff — re-hashed, and wrapped in a receipt binding schema, index, content hash, row count, activation identity, and account provenance. Every later consumer re-opens and re-hashes these exact bytes; the executor does it again immediately before evidence access.

    out NativePrefixProduct — content-addressed · byte-reopenable · causally trimmed
  5. Features & indicators pm_core.FeatureComputer · at search time, never stored

    Indicators (EMAs, ATR, ADX, structure levels, volume features…) are computed on demand from the sealed prefix, never precomputed and stored — there is no stale indicator cache to drift from the data. Each strategy declares its required features, and the identity of the feature code itself (a hash of pm_core) is pinned into every trial artifact — change the indicator math and the identity of everything built on it changes. Warmup is a verified quantity: each strategy declares minimum bars, and state-dependent features additionally require authenticated predecessor context, not a guessed constant.

    in sealed prefix  →  out feature frame in memory, code-identity pinned
  6. Regime classification frozen detector · four regimes

    Every bar is classified TREND / RANGE / BREAKOUT / CHOP by a regime detector whose parameters are fitted on training data only, then frozen and hash-recorded. The same frozen detector record follows the winner into live trading — the runtime is hash-verified to run the exact detector its book was validated with. Regime support counts become a receipt: a regime that never occurred in training is typed REGIME_UNOBSERVED with zero attempts, rather than force-fitted.

    out regime fit decision + per-regime support receipt (counts must sum to eligible rows)
  7. Cost surfaces Backtester · base + stress lanes

    Execution-cost inputs are frozen and provenance-bound: observed per-bar spreads (the base lane uses conservative-maximum spread mode); broker-bound volume, swap and instrument terms; and deployment-config commission and slippage assumptions. A second stress lane re-prices everything at empirically derived worse spreads (P90/P95/max of the same closed partition) — and a stress lane numerically identical to base is itself rejected as invalid.

    out execution-spec receipt + BASE/STRESS cost-policy identities, frozen before any search

Operations

--optimize — what happens, in order

One unattended run. Each numbered step consumes the sealed outputs of the previous step, re-verifies them from bytes, and produces sealed outputs of its own. If any step fails, the run stops with a typed reason and the previous book remains untouched.

  1. Freeze the search domain planner

    The domain is committed before looking at any outcome. For each empirically observed cell, the current planner creates exactly 128 attempts: one full default for each of the 100 registered strategies plus 28 deterministic, outcome-blind non-default designs. It also freezes one timeframe-specific trailing depth selected from a ladder using source geometry only. The full parameter domains are recorded, but their Cartesian product is not exhaustively searched.

    scale observed cells × 128 attempts · unobserved regimes × 0 attempts · every attempted hypothesis counted
  2. Seal the data at each anchor native prefix producer

    For each of the 4 historical anchor dates and each symbol × timeframe, the activated dataset is causally trimmed at the anchor cutoff and sealed (see Data pipeline). Genuine terminal source absence becomes SOURCE_UNAVAILABLE. A corrupt source, identity mismatch, or infrastructure fault is TECHNICAL_FAILURE and aborts the generation; it can never be persisted as “no trade.”

    scale per anchor: 600 resolved source groups · one sealed prefix per available group · authenticated terminal state for genuine source absence
  3. Run the historical search authoritative executor + Backtester

    Per cell, per attempt: features are computed from the sealed prefix, the strategy generates signals, and the real backtest engine executes them with full costs in both lanes (base and stress). The same attempt's strategy, parameters, and depth are tested on four rolling-origin inner folds. Each has at least 63 unseen days, for at least 252 validation days in total; dependency-derived purge gaps keep its preceding fit slice away from validation. Every trade becomes a position-event record (entry/exit time, order counters, P&L, risk) — the raw atoms of all later statistics.

    out per attempt × fold: position events + daily mark-to-market series, staged to bounded immutable files
  4. Select winners under multiplicity control TradePower + Winner V11

    Selection runs the gauntlet: trade-power floors (enough effective, autocorrelation-adjusted trades to mean anything — calibrated on training, enforced on validation), exact accounting identities (daily sums must equal per-trade sums to the last decimal), stress-lane survival, and deflated significance counting all committed attempts, including failures. A cell with real data but nothing surviving becomes NO_WINNER or INSUFFICIENT_EVIDENCE, both bound to the rejection evidence.

    out per anchor: all 2,400 cells typed and hash-committed; any TECHNICAL_FAILURE or UNSEARCHED cell makes the generation incomplete
  5. Replay each anchor book forward forward-OOS replay producer

    Each anchor's independently selected winners then run as a synchronized portfolio over an exact 365-day outer period after that anchor — data that played no part in selecting that anchor book. Real fills at executable bid/ask, shared capital admission, full round-trip costs, margin, exposure — with a strict valuation order (close existing, then mark, then admit) that kills same-bar lookahead.

    out six content-addressed ledgers × 4 anchors — the only inputs causal validation accepts
  6. The causal gate causal process decision

    The one question that matters: did the selection process, applied at past cutoffs, actually work on data it had never seen — as a portfolio, after costs? The decision is re-derived from the sealed ledgers by an independent evaluator plus its own verifier. FAIL stops the run here. No current book is minted from a process that didn't prove itself forward.

    gate OFFLINE_PROCESS_VALIDATION_PASS — recomputed, never accepted from a flag
  7. Mint the current book current-refit producer (in progress)

    Only after PASS, the entire identical search process runs again at the latest fully closed common cutoff. It does not deploy an old anchor winner. The current run evaluates the same frozen 128-attempt design on fresh cutoff-local evidence, may select a different strategy and parameter vector, and then refits that selected vector on its tested trailing depth ending at the cutoff. Parameters are decoded and round-tripped through the live strategy registry; the physical ledger is reconstructed from verified artifacts and stamped for demo probation.

    out the deployable winner book + raw manifest — every entry traceable to its full evidence chain
  8. Calibrate capital portfolio replay + Capital V8

    The whole book replays as one account under a frozen roster of up to 64 multi-axis policies. Its total-stop-risk axis must cover at least 3 / 5 / 8 / 10 / 12 / 20 / 33.25 / 50 / 75 / 90%, alongside frozen same-symbol, factor, margin, free-margin, drawdown, and gap-stress limits. Historical inner periods select a policy and unseen outer periods test that selection rule; the latest 365-day current-selection period chooses the present envelope. The selected cap is evidence-driven and may be low; 33.25% or higher is never presumed.

    out signed capital envelope — the maximum total stop-risk the runtime may hold
  9. Assemble, re-verify, publish coordinator + journaled CAS

    A final assembly re-verifies the complete chain from raw artifacts — seven authority indexes and a chain receipt. Publication journals its intent, compare-and-swaps the ledger, writes the manifest, and confirms. A crash at any instant leaves either the old book or the new book, never a hybrid; recovery is deterministic from the journal.

    out promoted generation · previous book preserved · eligible for the separate raw readiness preflight, which may still refuse

One cell means one symbol × timeframe × observed regime. A candidate does not win by having the highest headline return; it must survive every earlier row before comparison is allowed:

Two different meanings of “dependence”

Gate 6 measures temporal dependence inside one candidate's own evidence. It asks whether its apparent 40 trades or 252 days contain enough independent information to support an edge estimate. It does not compare EURUSD with GBPUSD, prefer low-correlation cells, or delete a qualified winner because several specialists share USD exposure. Cross-cell interaction appears only after every local winner has been retained, in synchronized account replay. There, total stop risk, same-symbol exposure, currency-factor concentration, margin and gap loss are policy axes to test quantitatively—not alternative definitions of which strategy won its cell.

An unresolved methodology boundary: PBO and bootstrap

Winner V11's new production decision uses exact-attempt DSR, HAC/sensitivity-HAC and precommitted block dependence inference. It does not currently contain a PBO or moving-block-bootstrap admission gate. PBO/bootstrap implementations still exist in the legacy pm_pipeline; the separate synchronized current-portfolio replay uses a sequence bootstrap for ruin/drawdown stress. Those are not the same as wiring PBO/bootstrap into the genuine raw Winner V11 chain. Therefore the stated production requirement for per-cell DSR/PBO/bootstrap has not yet been fully met and must be resolved before the full optimization; legacy results cannot be cited as if they passed the new authority seam.

Multiplicity, without the statistics vocabulary

Trying 128 candidates is like buying 128 lottery tickets: even if every candidate has zero true edge, one may look excellent by accident. FxPM records every ticket, including failed executions, and makes the apparent winner clear a harder DSR benchmark. Expanding the roster can discover better parameters, but it also raises the luck penalty and the evidence needed to tell signal from noise.

Current status

This is the intended production chain, not a claim that the command already performs it. Several standalone stages and the authenticated anchor plan are reviewed, but the complete pre-policy Capital candidate path, current-mode raw cross-binding, coordinator wiring, and a real bounded end-to-end canary remain open. The --optimize entry point still routes to the legacy generation path and must not be treated as production-ready until those seams land and the canaries pass.

Operations · experiment design

Folds, anchors, and why the current book is fresh

There are three different clocks in the optimizer. Confusing them makes the process look like one stale parameter vector is run four times. That is not the intended design.

The short answer

The four 63-day folds are inside one search at one cutoff. They compare a precommitted roster of candidate strategy/parameter vectors. The four historical anchors are separate past cutoffs. At every anchor the entire search is run again, so that anchor may choose a different strategy and parameters. Its resulting whole book is then tested for 365 genuinely later days. Only after those repeated process tests pass is the same entire search run again through the latest closed cutoff to create today's book.

What historical PASS approves—and what it does not

The causal result is a license to rerun a method, not a certificate for an old set of parameters. This distinction is the dependency that makes the current output meaningful:

Inherited into the current rerunRecomputed at the latest cutoffNever inherited as current evidence
The process definition; exact 128-design roster and ordering; complete parameter-domain record; timeframe depth ladders and largest-feasible outcome-blind rule; fold/purge geometry; eligibility, TradePower and Winner gates; code, feature, regime, data and cost pins; sparse state rules; causal PASS identity. Latest causal source prefixes; current regime fit and occupancy; the raw four-fold position events for all 128 attempts; TradePower/DSR/score; the current winning strategy and parameter vector (or abstention); cutoff-local refit artifacts; synchronized current candidates; current book and current Capital policy. The strategy/parameters that won at any historical anchor; an anchor's return score; outer-period trades as weights for current candidate ranking; a claim that an old parameter itself has four years of OOS proof.

A latest-cutoff search depends on history because its authorization receipt must bind an independently verified historical causal PASS. But the current ranking does not consume the outer winners or losses. The market bars from those calendar years may legitimately appear in a current trailing training window—by now they are past and knowable—but they enter under the same frozen rules for every current candidate. Using the outer results to change the roster, score, thresholds or depth after inspection would turn test evidence into design data and void the PASS; the changed process would need all anchors rerun.

A worked cell example

Hypothetical only—this is not a reported FxPM winner

At historical cutoff A1, take EURUSD × H1 × TREND. The frozen planner creates its 128 attempts. Attempt 42 uses one fixed strategy, parameter vector and H1 depth across four rolling validation folds; attempt 87 uses a different precommitted design. Winner V11 may select attempt 42, reject all 128, or mark the evidence insufficient. The same happens independently for every other cell. Selected cells are refit through A1's cutoff, forming Book A1, then—after purge—the whole Book is replayed for the next unseen 365 days.

At A2 the entire search starts again from the same rules. Changed market evidence may make attempt 87 win, a different strategy win, or produce no winner; A1's attempt 42 is not carried forward by privilege. After A1–A4, the four synchronized unseen account histories answer only: “Did this selection/refit process generalize?” If that answer passes, the current cutoff repeats all 128 trials again. Suppose current attempt 91 wins: attempt 91—not A1's 42, A2's 87, or the best-looking outer result—is the only parameter vector eligible for the current book.

Inside one anchor: what the four folds actually do

For one observed cell, the current planner freezes 128 attempts before evidence is read. For each attempt, the strategy and its parameters stay fixed across the four folds. The fit and validation windows move forward:

time ───────────────────────────────────────────────────────────────→ fold 1: [ trailing fit window 1 ][purge][ unseen validation 1: ≥63d ] fold 2: [ trailing fit window 2 ][purge][ unseen validation 2: ≥63d ] fold 3: [ trailing fit window 3 ][purge][ unseen validation 3: ≥63d ] fold 4: [ trailing fit window 4 ][purge][ unseen validation 4: ≥63d ] No validation interval overlaps another. No later fold can change the attempt roster.

All completed position events and daily base/stress returns from the four folds feed Winner V11. The primary score is the worse of the base-cost and stressed-cost, dependence-robust lower confidence bounds on daily log growth. The selector also requires adequate effective days and trades, attempt-aware significance, accounting identities, positive overall log growth, and positive mean log growth in both the worst and newest fold under both cost lanes. A per-fold confidence bound is reported as a diagnostic; requiring four separate significance tests was deliberately rejected because it destroys statistical power.

Deterministic does not mean certain

Given identical frozen bytes, code, and clock inputs, the score and winner are reproducible. The score is still an estimate from noisy market history. FxPM selects the best admissible candidate in the tested roster; it does not discover a provably optimal law of the market.

What “edge decay” currently means

The frozen production path has concrete recency defenses: shorter M5 depth, a positive newest inner fold, a positive newest outer anchor, full latest-cutoff reselection, and runtime validity-through/retrain-due fields tied to an edge-decay receipt. Causal v8 itself does not fit and publish a numeric timeframe-specific decay curve or half-life. Until a genuine current run produces and verifies those expiry calibrations, “edge decay is handled” would be too strong; this remains an evidence item for the pre-run design and later canaries.

Freshness: there is no untrained final year

The corrected target calendar reserves the final 365 days before the current cutoff as a CURRENT_SELECTION window and ends historical outer proof immediately before it. That does not leave the latest year ignored. After causal PASS, the current search consumes the causal prefix through the latest fully closed cutoff. Its selected strategy is then refit on the tested trailing depth ending at that cutoff. The final year also supplies current Capital policy selection. What the current book necessarily lacks is future evidence after its own creation; that is why it begins at probation size on demo.

The process is frozen; the old parameters are not. “Refit” here has two parts that are easy to collapse mentally:

  1. Rerun selection now: reevaluate the complete precommitted candidate roster on current cutoff-local evidence and choose today's eligible winner for each cell.
  2. Fit the chosen current winner: realize its validated trailing depth ending at the latest cutoff, build the current regime/controller bindings, and mint deployable artifacts. This step may fit the state explicitly allowed by the frozen recipe; it does not get a second opportunity to alter the chosen strategy or parameter vector.

A real methodological limitation

The current planner does not empirically compare several depths and does not exhaust every point in every strategy grid. It represents all 100 strategies at defaults plus 28 deterministic non-default designs, then chooses one depth from source geometry. This keeps the immutable roster within Winner V11's 128-attempt bound and makes multiplicity/resource use tractable, but “best” means best among those 128 attempts. Untested parameters and a possibly better depth remain unknown. Changing this requires a new precommitted design and fresh outer validation; it cannot be patched after seeing results.

Every expert is replayed on one synchronized account rather than adding standalone returns. Existing positions close, then remaining positions are marked, then new candidates are admitted. Admission uses per-trade risk (normally about 0.25%), total stop risk, same-symbol risk, factor concentration, margin and free margin. The bounded roster may contain up to 64 policy points and must cover total-stop-risk candidates from 3% through 90%; each point also specifies factor, same-symbol, margin, free-margin and gap axes. A high cap is an option to test, not a target.

--trade --paper — demo probation

Paper mode executes the freshly validated book against a real broker — real order round-trips, real fills, real spreads — on the authorized FBS demo login 106165989. It is the mandatory probation period between statistical validation and any funded capital. The command must include both flags; --paper by itself does not enter the trading loop.

  1. Runtime identity preflight

    Before any order: the connected MT5 account's login must be exactly 106165989 and the broker-reported trade mode must be DEMO. The final send boundary refreshes the broker snapshot, requires DEMO mode, and requires the observed login to match the connector's configured identity pin. Therefore the demo runtime must use a separately verified pin for 106165989; merely logging the terminal into demo is not enough. Account-bound receipts keep demo evidence separate from funded evidence.

  2. Book authority check

    Only a PROCESS_VALIDATED_CURRENT_REFIT book that passes demo-probation readiness executes. The legacy self-asserted demo path was deleted. The live regime detector is hash-verified to be the exact frozen detector the book was validated with.

  3. Execution loop

    Signals evaluate on closed bars; orders carry the book's magic number and an attribution comment namespace; position sizing stays inside the capital envelope. Expired winners stop opening new positions rather than trading on stale authority.

  4. Attributed forward ledger

    Every closed deal is fetched from broker history and attributed back to the exact cell, strategy, and parameters that produced it — into a telemetry store physically separate from the book (runtime can never mutate promoted authority bytes).

  5. Probation evidence review

    You compare forward outcomes to validation expectations: hit rates, cost realism, regime behavior. This evidence feeds the live-readiness gate — and your go/no-go decision.

Operations

--trade — live operation

Live mode runs the same execution loop as paper, but crossing into funded territory requires passing every readiness gate — and funded capital authorization is cryptographically two-staged so no run can self-authorize risk.

  1. Readiness preflight --preflight

    Every gate re-checked from raw artifacts: the authority chain receipt (book traces byte-for-byte to a complete verified generation), probation evidence present, detector binding, capital envelope validity, winner expiry, account scope. Any failure reports the exact gate and refuses.

  2. Funded authorization — stage one

    The runtime issues a content-addressed authorization request bound to this exact generation and capital selection, and halts as PENDING. By design the first request always pends — even if a valid response is already staged — so live risk always involves a second, later step.

  3. External signature — outside the process

    The request is signed externally (Ed25519) with a key the trading process does not hold — the funded boundary exposes no signing capability, only a trusted public key. Scope separation is cryptographic: a demo authorization cannot be replayed onto a funded account, nor across generations.

  4. Stage two — verify and go

    On the next invocation the signed response is verified against the trusted key and the exact request bytes; only then does the loop trade — inside the signed total-risk cap.

  5. Ongoing discipline

    Scheduled refits re-run the full chain before expiry (no shortcut re-validation); fill/cost drift accumulates in isolated telemetry feeding the next validation; a publication that required crash recovery is typed as such and cannot count as a routine promotion.

Standing boundary

There is currently no funded-live GO. No funded or live order is ever sent without explicit operator instruction. Every evidence-producing stage declares grants_trading_authority: false in its receipts — trading authority exists only at this gate, only with the external signature.

Foundations

Integrity principles

Five rules, applied uniformly from data acquisition to publication. Most of the defects caught in review were violations of exactly one of these.

1 · Derive, never accept

No component believes what a caller tells it. Identities are recomputed from bytes; parameters are round-tripped through the live strategy registry; counts are re-counted from reopened source files; rosters are re-derived and compared. Where two authorities must agree across different schemas, they are joined by an explicit frozen cross-binding — never by pretending their hashes are equal.

2 · Fail closed, with types

Every failure has a typed code stating exactly what failed. No generic fallback, no silent skip. A production run either completes with full evidence or stops with a precise reason — and infrastructure failure aborts rather than being recorded as any market state.

3 · Commit before you look

Search domains, attempt rosters, fold geometry, cost policies, and capital constraints are frozen and content-addressed before evidence is accessed. You cannot widen a search, drop a failure, or tune a window after seeing outcomes — the commitment already exists in immutable storage and everything downstream binds to it.

4 · Count everything

Search enough and something will look good by chance. Every attempt — including rejections — enters the attempt ledger and deflates the significance of whatever wins. Trade-power floors ensure a winner has enough effective sample to mean anything; identical trials at different training depths count as distinct hypotheses.

5 · The whole vocabulary of honesty

Every cell in the 2,400-slot decision resolves to exactly one recorded disposition. A generation containing TECHNICAL_FAILURE or UNSEARCHED is incomplete and cannot publish:

SOURCE_UNAVAILABLEVerified terminal source absence, with no technical/provenance failureNon-economic; never a market verdict
REGIME_UNOBSERVEDThe regime empirically never occurred in training dataZero attempts; complete, non-vetoing

The two-agent review protocol

All substantial changes flow through a hash-chained coordination ledger: a lane is claimed, the work is frozen to exact per-file hashes, and the other agent reviews the same bytes. The review priority is trading correctness and statistical validity: chronology, data geometry, cost stress, genuine evidence, deployed-model parity, bounded execution and failure semantics. Content hashes are operational drift checks, not a claim that a single-user laptop needs an elaborate adversary model. Critical correctness seams may get a second independent reviewer.

Recent catches, as a flavor of what this process finds: a deployment-window bias that would have degraded live performance versus backtests; a missing complete pre-policy Capital roster; a stress lane that could be a numerical no-op; and an integration premise that synthetic fixtures satisfied but genuine evidence never could. Those affect expected performance or reliability and belong on the critical path.
