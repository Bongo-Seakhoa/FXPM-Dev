FxPM Order Flow Audit

Generated: 2026-04-02 | Scope: live order flow, scaling, sizing, broker execution, active order management, same-symbol risk handling, and config authority.

This audit intentionally did not re-litigate accepted strategy-specific or PM-specific design choices that are already part of your operating doctrine. It focused on whether the current implementation is faithful to your intent, operationally trustworthy, and internally consistent.

Amber Trust with caveats

Primary entry flow is materially strong. Config-first propagation, MT5 preflight, broker-aware stop validation, contract-math risk sizing, hard per-trade caps, same-symbol risk checks, margin protection, and restart-safe position recovery are all present and covered by tests.

The two biggest trust blockers are active-path accounting gaps, not philosophy gaps: open-position risk metadata currently stores target risk instead of actual post-sizing risk, and one fail-closed secondary-trade branch can reference variables before assignment. Also, scaling and the richer order-management toggles are not active in the live MT5 loop, so they should not be relied on operationally today.

Findings First

High

Open-position risk metadata records target risk, not actual post-sizing risk

Why it matters: same-symbol risk accounting later reads risk back from position comments. If min-lot flooring, volume-step normalization, SL widening, or fill drift pushes actual risk above the target, the open position can be undercounted in future combined-risk checks.

Evidence: pm_main.py:2512-2517 writes risk_pct=target_risk_pct into the trade comment, while later risk reads use TradeTagEncoder.get_risk_pct_from_comment(...) in pm_main.py:2217 and pm_main.py:2289.

Impact: the active same-symbol exposure model is directionally correct, but it is not fully faithful whenever actual risk exceeds target. This is most relevant on symbols where 0.01 lots often over-risks relative to the requested target.

Recommendation: persist actual post-normalization risk in the comment or reconstruct it from durable metadata after execution. Do not continue using target risk as the stored exposure proxy for live risk aggregation.

High

Secondary-trade fail-closed path can reference variables before assignment

Why it matters: in the branch that blocks a secondary trade because the position snapshot is unavailable, the actionable log path references volume and actual_risk_pct before those variables are defined.

Evidence: pm_main.py:2273-2282.

Impact: the intended fail-closed branch can itself throw an exception instead of logging and returning cleanly. This is a latent reliability bug in an error-handling path.

Recommendation: write None for values not yet computed, or move the block after sizing. This should be fixed before claiming the secondary-trade path is fully hardened.

Medium

Scaling flags exist, but scaling is not implemented in the live order engine

Why it matters: enabling scaling in config currently does not produce scale-ins, additional entry logic, or live position additions through the MT5 loop.

Evidence: pm_position.py:281-283 defines allow_scaling, max_scale_ins, and scale_in_pct, and pm_position.py:339 tracks scale_count, but there is no live execution usage outside those definitions.

Impact: turning scaling on today gives a false sense of live capability. Operationally, nothing happens.

Recommendation: either wire scale-ins explicitly into the MT5 live loop or document these settings as dormant/non-live.

Medium

Trailing stop, breakeven, and time-based exit helpers are not wired into the live MT5 loop

Why it matters: the standalone PositionManager has working helper methods for trailing, breakeven, and max-duration exits, but the live trader does not call them or mirror them into modify_position() requests.

Evidence: helpers exist at pm_position.py:827-908; live order flow in pm_main.py uses initial SL/TP, opposite-signal close, and margin-protection close, but no active modify_position() path.

Impact: these config toggles should not be treated as live protections today. They are helper seams, not active broker-side order management.

Recommendation: same as scaling: either wire them into the live MT5 loop or mark them clearly as non-live helper fields.

Medium

Broker symbol resolution failures degrade or skip live trading for affected instruments

Why it matters: startup spec sync logs a warning and falls back to config values when broker aliases are unresolved, but live symbol processing later returns immediately if the symbol still cannot be resolved.

Evidence: sync warnings at pm_main.py:697-700; live per-symbol processing returns on unresolved broker symbols at pm_main.py:1289-1290.

Impact: unresolved CFDs/crypto pairs are not just less precise; they are often effectively non-tradable in the live loop unless the broker alias is recognized.

Recommendation: add broker alias mapping for your unresolved symbols or expose a config-backed symbol alias table as an authoritative extension point.

Low

config.json contains duplicate pipeline.risk_per_trade_pct keys

Evidence: config.json:6, config.json:11, and the operative live field at config.json:88 under position.

Impact: the runtime currently behaves correctly because live entry uses position.risk_per_trade_pct when present, but the duplicated pipeline keys create avoidable ambiguity during reviews and incident response.

Recommendation: remove the duplicate pipeline entries so config remains unambiguous as the single source of truth.

Verified Strengths

  • Config-first risk basis is now correct. The live entry path starts from position.risk_per_trade_pct, uses position.max_risk_pct as the hard cap, and respects pipeline.min_trade_risk_pct as a viability threshold rather than a forced floor.
  • Risk scalars are no longer silently default-on. live_risk_scalars_enabled is default-off in pm_core.py:583 and only activates overlays when explicitly enabled in pm_enhancement_seams.py:492-500.
  • Spread overlay remains explicitly config-gated. It can block or soften the effective target only when execution_spread_filter_enabled is on, which matches the current config-first model.
  • Execution uses broker-aware pricing and contract math. The live path sizes from MT5 order_calc_profit first, then falls back to tick math, and only lastly to pip-value math.
  • Broker-side protection is strong. Market orders validate side-correct SL/TP placement, stop-distance rules, filling mode, and order_check() preflight before submission in pm_mt5.py:691-824.
  • Stop widening preserves the validated reward:risk relationship. The live path widens only when required by broker stop-distance constraints and recalculates TP to preserve the original R multiple.
  • Entry duplication is throttled. Decision throttling prevents the same decision on the same bar from being retried or re-logged repeatedly.
  • Live fail-closed behavior is generally good. Missing symbol info, missing ticks, missing account info, margin stress, and unresolved position timeframe metadata all block trading rather than trading blind.
  • Margin protection is real and tested. The current margin cycle closes losers first in recovery/panic states and is covered by dedicated tests.
  • MT5 fill-price logging is improved. The connector no longer prints 0.00000 when MT5 omits the returned fill price; it falls back to the requested execution price for logging continuity.

Trust Verdict

Can you trust the live order flow today? Yes for the primary entry path, with caveats.

  • You can trust the config-first sizing basis, broker-aware pricing, hard risk cap enforcement, stop validation, preflight, same-bar decision throttling, and margin protection.
  • You should not treat scaling, trailing stop, breakeven, or max-duration fields as active live behavior.
  • You should treat same-symbol exposure accounting as directionally correct but not fully faithful until comments store actual risk rather than target risk.
  • You should treat unresolved broker-symbol warnings as operationally significant because they can prevent live trading on those instruments.

Operational confidence level: strong enough for disciplined live use on well-mapped symbols, but not yet "fully trust without caveats" until the two high-severity findings are resolved.
