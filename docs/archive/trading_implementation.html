FXPM Trading Implementation Audit

Date: 2026-04-25 | Scope: preparing FXPM for live proof-of-ability trading on a $25 account | Method: codebase audit plus targeted runtime and config implementation

This document focuses on what the PM needs in order to function meaningfully on an ultra-small balance during a temporary, deliberately high-risk proof phase. The core question is not whether the PM should become conservative; it is whether the live stack can express valid winners cleanly at broker-minimum size while still preserving real execution discipline.

Main conclusion FXPM does not need a redesign for this temporary mode. The core issue was never the discovery engine; it was the live expression of winners at 0.01 lot on a tiny balance. This pass keeps the tournament broad and fixes the highest-value downstream execution gaps.
Primary blockers The hard constraints are still broker min-lot granularity, spread and commission drag, broker stop-distance rules, and real margin feasibility. Commission-aware risk math, projected margin checks, winner-ledger isolation, decision-time regime lookup, margin reopen hysteresis, and fresh duplicate-position guards are now implemented.
Best first move Run the shipped high-risk profile in config.json, keep the full live symbol set active, and let real feasibility determine what opens now versus later as the account grows.
Philosophy alignment The recommended changes stay downstream of winner discovery. They change live expression and live account handling on a tiny balance, not the upstream strategy tournament.

1. Scope and Method

The findings below are split into two buckets:

Config-first the PM can already behave differently through settings and profile choice.

Code-path the runtime logic that previously distorted tiny-account live trading has now been tightened where the fixes were high value and low regression risk.

This audit is grounded in the current code and docs, especially config.json, pm_main.py, pm_core.py, pm_mt5.py, pm_position.py, pm_enhancement_seams.py, README.md, and SETUP_AND_RUN.md.

4. Config-First State Now Shipped in the Repo

4.1 Live risk profile is now explicitly micro-account and high-risk

  • position.risk_per_trade_pct = 2.0, position.max_risk_pct = 3.0, and allow_min_lot_risk_clamp = true now give the live path room to express valid micro-account trades while still honoring a real hard cap.
  • pipeline.risk_per_trade_pct = 1.0 stays at a standard baseline so the temporary live account expression does not quietly push the upstream tournament itself into a tiny-account risk posture.

4.2 Risk basis is now set for temporary proof-mode deployment

  • The active profile now uses risk_basis = "balance". On a tiny account this prevents open PnL from hollowing out the next trade too aggressively during the proof phase.

4.3 Spread and same-symbol controls are still real, but now looser

  • The spread overlay remains on, but the shipped proof profile now uses min_edge_mult = 1.25, spike_mult = 3.0, and penalty_start_mult = 0.75 so it is less hair-trigger on a tiny account.
  • secondary_trade_max_risk_pct = 1.0 and max_combined_risk_pct = 4.0 remain same-symbol controls, not umbrella portfolio lockouts, but they now leave more room for local winners to stay active.

4.4 Margin thresholds are now explicit rather than hidden in dataclass defaults

  • The proof profile now exposes the full margin ladder directly in config as 80 / 65 / 50 / 90 for entry block, recovery, panic, and reopen, with a shorter 5-minute reopen cooldown.
  • The runtime now treats margin_reopen_level as a true recovery threshold after margin stress or a forced close. Missing margin_level is neutral only when no margin is in use; with open exposure it blocks new entries until account data is trustworthy.

5. Code-Path Constraints and What Was Implemented

5.1 The broker min-lot floor is the main executable bottleneck

The live path in pm_main.py does not behave like the standalone sizing helper in pm_position.py. Live trading clamps to broker minimum size, then lets the hard cap decide whether the trade survives.

  • Target risk amount is computed from account balance or equity: pm_main.py:3414-3420, pm_main.py:3567.
  • Broker minimum volume is enforced by min_vol = max(config.min_position_size, symbol_info.volume_min): pm_main.py:3570.
  • Actual post-normalization risk is then checked against the hard cap: pm_main.py:3645-3690.

5.2 Live pre-entry risk now includes commission

The live path now uses a shared cost-aware stop-loss helper. It still estimates stop risk from MT5 contract math first and deterministic fallbacks second, but it no longer omits commission on a tiny account.

  • Live stop-risk and post-fill telemetry now use the same helper path in pm_main.py.
  • Backtest commission deduction remains in pm_core.py, so live and research now agree on the one-way commission model.

5.3 Broker metadata overwrites config assumptions at runtime

  • tick_value, tick_size, volume_step, min_lot, max_lot, spread_avg, and point/digit metadata are refreshed from MT5 symbol info. Evidence: pm_core.py:1430-1450.
  • That means a permissive tiny-account config is not sufficient on its own; the live broker can still make a symbol economically or operationally impossible.

5.4 Projected margin sizing is now implemented

  • The PM now estimates required margin before submission using an order_calc_margin-style wrapper in pm_mt5.py and blocks locally when free margin is not sufficient.
  • order_check still matters as the broker's final authority, but many impossible micro-account orders now fail cleanly inside the PM first.

5.5 Min-lot handling is now configurable instead of silently divergent

  • pm_main.py still uses live-authoritative clamp-and-cap behavior.
  • pm_position.py now has an explicit allow_min_lot_risk_clamp seam so the same philosophy can be opted into without forcing it globally.

6. Instrument Economics Under a Full-Symbol High-Risk Mode

The broad universe is not economically neutral on $25, but that does not mean the PM must be narrowed. In the intended high-risk proof mode, the full symbol set can remain active while real feasibility checks decide what can actually open at the current account size.

Direct answer to the central question: proactive symbol limitation is not necessary for this mode. The existing live path already applies natural executable filters through min-lot sizing, hard-cap checks, broker stop rules, margin gating, and MT5 preflight. If those filters reject a trade, that is an acceptable outcome of the high-risk proof phase rather than evidence that the symbol should be removed from the PM universe.

  • Major FX pairs are the harshest micro-account case in the current config because 0.01 lot is already around $0.09-$0.10 per pip and commission is non-trivial.
  • XAUUSD and the low-friction index complex are structurally friendlier on pip-value grounds, though live margin and stop-distance must still be confirmed.
  • Crypto is mixed: some symbols have low nominal pip risk but meaningfully higher spread drag.
  • Low pip value alone is not enough. Exotics like EURZAR, GBPZAR, and USDZAR look cheap per pip but are still expensive once spread and commission are included.

Correct implementation stance for this mode: keep the full symbol set active and accept that some symbols will simply surface non-actionable or rejected trades until the account grows enough for them to become executable. The economics above should be read as explanatory context, not as a requirement to pre-limit the PM universe.

Optional operator use only: if you ever want a cleaner diagnostic run, the low-friction index complex and selected metals are the friendliest starting points, but that is now an optional convenience rather than part of the recommended high-risk live profile.

7. Recommended Operating Model: Two Explicit Live Profiles

The cleanest reversible path is to run two explicit profiles through the startup surface that already exists.

Profile Purpose Startup surface Important note
Small-account high-risk proof mode Temporary proof-of-ability on a micro balance where the PM must stay active and accept higher local risk. python pm_main.py --trade --config config.json Keep the full symbol universe active and let live feasibility determine what actually opens.
Standard larger-account live mode Normal live deployment once capital is large enough to support more reasonable risk and broader symbol breadth. python pm_main.py --trade --config <standard-profile.json> Restores safer settings and a broader symbol set.

Good news: the code already supports separate configs through --config, can isolate most runtime artifacts through pipeline.data_dir, pipeline.output_dir, and pipeline.log_dir, and now also supports a configurable validated-winner ledger path.

Current shipped state: the small-account profile isolates its winners in pm_configs_high_risk.json through pipeline.winner_ledger_path.

Why this remains aligned with PM philosophy: this split happens after winner discovery. It does not curate or narrow the tournament itself; it only changes the live account expression of winners once they already exist. In the small-account high-risk mode, even symbols that are not yet executable remain part of the live opportunity surface and can naturally become tradable later as capital grows.

Full-symbol interpretation: the high-risk small-account profile should not proactively narrow the live universe. If a symbol cannot currently open because of margin, min-lot, stop-distance, spread, or broker feasibility, that is acceptable; the PM can continue surfacing those opportunities until the account is large enough for them to become executable.

Confidence adjustment: the correct mindset for this temporary mode is more exploratory and less defensive than the earlier framing. The PM should be allowed as much breadth and freedom as possible, while real execution feasibility remains the final gate. In practice that means loosening non-feasibility restrictions and accepting repeated skips, rejections, and delayed activation on deeper symbols as normal behavior rather than something that must be designed away.

What not to do first: I do not recommend an internal "virtual 5000 notional" model as the initial fix. It adds abstraction but does not solve the broker's actual min_lot, spread, stop-distance, or margin constraints.

9. Code Changes Implemented in This Pass

The PM did not need a full overhaul for this use case. The highest-value changes were narrow runtime fixes that improved tiny-account live behavior, artifact truthfulness, and optimizer/live alignment without narrowing the tournament.

Priority Change Implementation outcome
1 Commission-aware live risk and hard-cap math. Implemented through a shared stop-loss helper so sizing, open-position risk estimation, and post-fill telemetry all include commission when enabled.
2 Projected margin feasibility before request submission. Implemented through an MT5 margin wrapper plus a PM-side free-margin gate before send_market_order.
3 Configurable validated-winner ledger path. Implemented through pipeline.winner_ledger_path plus CLI threading so the temporary proof profile can keep its own winner chain.
4 Configurable min-lot clamp philosophy. Implemented as an opt-in seam in pm_position.py so the live clamp-and-cap behavior can be reused where wanted without forcing it globally.
5 Dashboard active-ledger and write-surface hardening. Implemented so the dashboard follows pipeline.winner_ledger_path by default, gates remote write APIs behind PM_DASHBOARD_WRITE_TOKEN, and refreshes root CSV data through a locked merge plus atomic replace.
6 Decision-time regime alignment. Implemented so live winner lookup now prefers REGIME_LIVE / REGIME_STRENGTH_LIVE, matching the optimizer and backtester decision surface.
7 Margin reopen and account-snapshot safety. Implemented stateful reopen hysteresis using margin_reopen_level, with fail-closed handling for missing margin level when margin exposure exists.
8 Fresh final duplicate-position check. Implemented so final order submission refreshes exact/symbol broker positions after the sweep snapshot and fails closed if the fresh snapshot is unavailable.
9 Artifact and cache telemetry truthfulness. Implemented validation evidence, no-trade reason preservation, data-window fingerprints, ledger completion status, and resample-cache hit/miss/read/write telemetry.
10 Symbol viability report. Still optional future observability work. It would be useful, but it was not required to put the high-risk mode into a materially better live state.

What does not need changing: the discovery engine, the regime framework, the broad strategy tournament, and the main execution-orchestration architecture. The issue is executable trade expression on a tiny account, not the PM's core research identity.

10. Transition and Reversal Logic

The move back toward a normal live profile should be explicit, manual, and review-based. The repo already supports restart-based profile switching through --config; it does not support automatic account-balance-triggered switching, and that is acceptable for now.

10.1 Recommended transition ladder

  • Stage A: under $100 - stay in the small-account high-risk profile, keep the full symbol universe live, and review every weekly check plus every two-week retrain boundary.
  • Stage B: $100-$500 - step down toward 1.5% target risk and 2.5% hard cap, start re-tightening the spread overlay, and keep reviewing which parts of the broad universe have become genuinely executable rather than merely visible.
  • Stage C: $500-$1000+ - move toward the standard larger-account profile at the next structured review if order-check failures, margin events, and min-lot blocks are no longer dominant.
  • Stage D: around $5000 - operate fully on the standard profile and retire the micro-account proof mode rather than letting it become permanent by accident.

10.2 Review gates before stepping down from the proof profile

  • MT5 insufficient-funds or invalid-volume failures are no longer common.
  • The account spends most of its time in NORMAL rather than BLOCKED, RECOVERY, or PANIC margin state.
  • Min-lot normalization is not constantly forcing actual risk to the hard cap.
  • The proof profile is producing real executable trades rather than mostly near-misses and broker rejections.

Practical note: because the PM already uses a fixed two-week retrain cycle as its freshness mechanism, the cleanest moment to change profiles is a structured weekly review or a retrain boundary, not a silent mid-cycle auto-switch.

11. Final Audit Judgment

Bottom line: the FXPM live stack is now materially better prepared for a temporary micro-account proof phase. The remaining hard realities are min-lot granularity, spread and friction drag, broker stop rules, and genuine margin constraints, not missing core implementation seams.

Final answer on symbol scope: proactive symbol limitation is not required. In this temporary high-risk mode, the PM should keep the full symbol universe live and let real feasibility decide what opens now versus later as the account grows.

Best first action set: build a dedicated small-account high-risk config, run it with the full live symbol universe active, isolate outputs as much as possible, and then promote only the small set of code changes that improve live correctness without unnecessarily constraining the PM.
