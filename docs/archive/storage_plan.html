FxPM Final Storage Control Plan

Finalized on 2026-04-02 after reviewing the existing storage plan, the later suggestions, and the verified PM code paths. This document is a decision-ready plan only. No deletions were performed while preparing it.

Final verdict: The right storage strategy for FxPM is a PM-native, config-driven storage manager that keeps PM-owned data canonical and bounded, reduces MT5 history pressure structurally, and treats MetaQuotes cleanup as a guarded maintenance layer rather than the center of the design.

Current Disk Pressure

The latest check still shows critically low free space on C:, with about 5.14 GB free out of 475.92 GB.

Main Growth Driver

The largest uncontrolled growth remains MetaQuotes terminal and tester caches, not PM local CSV duplication.

PM Baseline

PM local market data is already mostly aligned with intent: one canonical symbol_M5.csv per symbol, overwritten in place.

Operational Priority

We need longevity without regression: no accidental loss of live trading continuity, restart recovery, optimization capability, or dashboard visibility.

Core Objectives To Preserve

Config Is Authoritative

Storage behavior must be governed by config. Code defaults exist only as safe backstops.

No Regression Of Function

Cleanup must never compromise live entry, protective exits, restart recovery, retraining, or dashboard continuity.

One Canonical Data Copy

PM should keep a single authoritative local market-data copy per symbol and update it by delta.

One True Growing Ledger

The only intentionally long-lived growth path should be the actionable signal and trade ledger. No-actionable noise and sweep heartbeats stay out.

Final Architecture

Target state: FxPM should own and bound what it creates, reduce how often it forces MT5 to expand its own caches, and treat external cleanup as governed maintenance rather than ad hoc deletion.

1. PM-Owned Storage Must Become Fully Bounded

  • Keep one canonical data/<symbol>_M5.csv per symbol.
  • On refresh, append only missing delta bars, then deduplicate, sort, compact, and cap to configured bar budgets.
  • Prune data/.cache by age, orphan state, source mismatch, and total size quota.
  • Replace unbounded or compatibility-only PM snapshots with bounded retention.
  • Keep last_trade_log.json and last_actionable_log.json as bounded latest-state files.

2. Replace Scattershot Trade Snapshots With One Canonical Actionable Ledger

  • Create a canonical ledger, preferably pm_outputs/signal_ledger.jsonl.
  • Write only actionable events to the ledger.
  • Explicitly exclude: NO_ACTIONABLE_WINNER_SIGNAL NO_ACTIONABLE_SIGNAL_WITHIN_MARGIN live sweep heartbeat
  • Allow the ledger to be long-lived, but segment it by month or size for safe rotation and dashboard loading.
  • Migrate the dashboard from wide scans of trades_*.json to the canonical ledger plus the latest-state snapshots.

3. Make Live Data Access Local-Data-First

  • Use PM local M5 data as the primary live-analysis source.
  • Refresh only missing delta bars from MT5 when needed.
  • Resample higher timeframes locally via DataLoader.
  • Use MT5 directly only for things that truly must be live: account info ticks positions order send modify close small delta refreshes

4. Add A Safe MetaQuotes Maintenance Layer

  • Implement it in Python first, with dry-run, manifests, path verification, protected roots, and post-clean validation.
  • Start with low-risk targets only: stale tester agent logs, old terminal logs, temp directories, installer leftovers, and clearly inactive tester bases.
  • Do not auto-prune active-server history until the local-data-first path is proven.
  • Any shell usage should be an implementation detail behind the same verified plan, not an operator improvisation.

Final Rollout Plan

Phase 0.5: Immediate Safe Reclamation

Because free space is critically low, there should be a short operator-side stabilization pass before or in parallel with code work. This phase is deliberately narrow: only clearly safe, noncritical reclaim targets should be touched, and only through a dry-run-first process. Exact commands belong in a separate runbook, not in this plan.

  • Confirmed low-risk reclaim target: once MT5 is fully stopped, remove or archive the inactive demo roots FBS-Demo and MetaQuotes-Demo.
  • Expected benefit: about 5.44 GB recovered, which is enough to more than double current free space.
  • Required safeguards: manifest the exact paths first, verify MT5 is not running, record pre-clean free space, perform post-clean verification, and confirm active real-server roots remain untouched.
  • This is part of the MetaQuotes maintenance scope, not the later active-root quota work.

Phase 1: Observe-Only Storage Governance

  • Add a storage section to config and the dataclass model.
  • Introduce a storage housekeeper invoked at the end of each live sweep.
  • In the first release, it measures only: sizes, growth rate, reclaim candidates, and threshold crossings.
  • Persist a compact state file such as pm_outputs/storage_state.json.
  • Use due-time comparison such as now >= next_due_at for cadence control rather than sleep-based waiting loops.

Phase 2: Bound PM-Owned Storage

  • Cap and compact canonical M5 files.
  • Add cache retention and orphan pruning for data/.cache.
  • Add retention-aware log rotation.
  • Put compatibility snapshots under bounded age or count retention.

Phase 3: Introduce The Canonical Actionable Ledger

  • Add signal_ledger.jsonl as the primary long-term history store.
  • Update the dashboard to consume it incrementally.
  • Keep legacy trades_*.json compatibility only until the dashboard migration is complete, then retain them minimally.

Phase 4: Local-Data-First Live Analysis

  • Change live sweeps to analyze from canonical local M5 data plus delta syncs.
  • Use MT5 direct bar pulls only when local data is missing or stale beyond configured tolerance.
  • This is the structural fix most likely to reduce future MetaQuotes history expansion pressure.

Phase 5: MetaQuotes Janitor

  • Enable automated cleanup for clearly safe MetaQuotes targets.
  • Treat confirmed-unused demo roots as early approved janitor candidates once the stop-MT5 precondition is met.
  • Keep active roots protected by default.
  • Require dry-run success and manifest verification before destructive mode.

Phase 6: Optional Active-Root Quotas

  • Only after Phase 4 has proven reliable in production.
  • Explicit opt-in only.
  • Idle-window only.
  • Protected minimum history must remain around the current live universe and recent optimization universe.

Housekeeper Cadence

Scheduling rule: The storage subsystem should not run as a separate sleep-based timer thread. It should piggyback on the existing PM runtime and decide whether maintenance is due by comparing datetime.now() with persisted desired run times such as next_due_at.
Cadence Allowed Work Why
Every live sweep Cheap checks only: free space, quota breaches, state update, threshold alerts Keeps overhead tiny and avoids interference with live trading.
Periodic maintenance window PM-owned cleanup such as cache pruning, log rotation, snapshot retention Bounded and safe work that does not need to run every sweep.
Explicit janitor cycle MetaQuotes cleanup after dry-run and path verification External-store cleanup is more delicate and should be isolated.
Post-optimization Targeted cache trimming plus explicit review of MetaQuotes Tester/*/bases/* artifacts Optimization is one of the times growth can spike suddenly, especially through tester-base downloads and caches.

Required Guardrails

These are mandatory for any automated cleanup path.
  • Resolve and verify absolute paths before any deletion.
  • Keep explicit protected roots for the active workspace, current PM outputs, and active MT5 roots.
  • Do not delete any file modified in the last 5 minutes.
  • Never let storage cleanup block protective trading actions such as close, modify, stop management, or restart recovery state writes.
  • If a storage emergency mode exists, it may only pause new entries when explicitly enabled in config and only after safe cleanup has already been attempted.
  • Maintain manifest logging for every cleanup action with path, reason, size before, timestamp, and result.
  • Run post-clean verification for PM health, critical file presence, and MT5 connectivity where applicable.
  • Keep dry-run as the default mode for new cleanup scopes until they have passed verification and tests.
  • Avoid dedicated sleep-driven janitor processes. Use comparator-based scheduling inside the existing live loop or maintenance entry points.

Operator Recommendations Outside The PM

These are good recommendations, but they are not the PM's job to enforce automatically.
  • Review whether the PM workspace should remain under OneDrive. This is operationally useful, but it adds sync churn and possible file-lock contention.
  • If the workspace stays in OneDrive, consider excluding or freeing up space for large regenerable folders such as local data and cache, subject to your backup policy.
  • Clean up the duplicate keys in config.json, especially the repeated pipeline.risk_per_trade_pct, so storage settings and all future config-driven behavior remain unambiguous.

Verification Gates

  • Functional parity: live sweeps, entries, closes, restart recovery, dashboard updates, and optimization must still work.
  • Safety parity: no accidental cleanup of active PM files or active MT5 roots.
  • Storage plateau: free-space trend must improve or stabilize after rollout, not just bounce once.
  • Observability: storage warnings must be visible without flooding the logs.
  • Rollback readiness: every destructive cleanup scope must be disableable by config.
Success condition: After rollout, the PM should be able to run indefinitely without PM-owned storage growing without bound, while MetaQuotes growth is reduced structurally and cleaned only through guarded maintenance.
