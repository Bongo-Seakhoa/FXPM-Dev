1 Audit verdict — does the best strategy reach the live market?

Yes, by construction, and the funnel is deliberately strict. Across all 100 symbols the optimizer evaluates a 100-strategy pool against every (timeframe, regime) cell, scores each survivor on a blend of its freshest-data performance and its persistence on the adjacent window, and stores only validated winners. A separate promotion gate then blocks everything that fails walk-forward or historical-stress evidence. Live trading consumes only promoted winners for the exact decision-time (timeframe, regime); there is no fallback to a "best available" unvalidated strategy.

What the audit confirmed:
  • Split geometry in DataSplitter.get_workflow_indices reproduces the documented 300k bleeding-edge layout exactly (verified by arithmetic and tests/test_data_splitter.py).
  • Train, validation, and eligibility run on three distinct slices; the train (newest 125k) and validation (adjacent 50k) windows are disjoint with a 300-bar embargo, so the robustness ratio is meaningful.
  • The optimization-time validation thresholds and the live re-check gate read the same config keys — a stored winner cannot pass selection but silently fail live, nor vice versa.
  • The promotion classifier, NO_TRADE markers, and winners-only live lookup are mutually consistent. Blocked / paper / no-trade cells are excluded from live at three independent points.
  • Live startup is fail-closed: account identity, equity floor, artifact-drift policy, kill switch, ledger freshness, and supervisor latch are all checked before any order. --trade returns exit code 2 on failure.
The one structural caveat (by design, not a bug): the validation window is older than the training window. Production optimizes on the freshest 125k bars and validates on the 50k bars immediately before them. This is a backward persistence check, not a forward out-of-sample test — it cannot detect overfitting to the newest window in the forward direction (there is no forward data; the newest bar is the live edge). The team chose this deliberately for a decaying FX stack. Section 9 details the tradeoff and the five mitigations that contain it.

4 Optimization stages (1–3) in detail

Stage 1 — Eligibility & screening (active 250k)

  • Every strategy is backtested on the full active universe. Optional screening ATR anchors (1×/2×/3×) prevent rejecting a strategy only because its default exit range was wrong.
  • Hard training-eligibility gates remove "obviously bad" strategies before expensive tuning. Current config: train PF ≥ 0.8, train return ≥ -15%, train DD ≤ 20%.
  • Regime-specialist rescue: a strategy weak on the full sample is kept if it is strong in at least one regime (≥25 trades, PF≥1.0, return≥0, DD within ceiling) — specialists are not discarded for full-sample mediocrity.
  • Top-K strategies per regime are identified from screening scores and passed to Stage 2.

Stage 2 — Tuning & per-regime selection (newest 125k) + (WFV)

  • Top-K strategies are hyperparameter-tuned with Optuna TPE (size-aware budget; 120–1500 trials/strategy) or grid search, on the newest 125k optimization surface.
  • Trades are bucketed by the decision-time regime label (REGIME_LIVE at the signal bar) for exact backtest/live parity.
  • For each (TF, regime) the winner is the highest-scoring candidate, where the score blends train (newest) and validation (adjacent) metrics with a robustness gap penalty (fx_gap_penalty_lambda=0.7), then descends top-K candidates until one passes the validation gate.
  • Optional false-discovery confidence multiplier (deflated-Sharpe / PBO machinery) scales scores; the hard DSR block is inactive in production (false_discovery_min_dsr=0.0).

Stage 3 — Governance / risk-management policy

  • Each surviving winner gets a risk/governance policy chosen by a local tournament (local_governance_tournament_enabled=true), selected on the stage3 surface (the bleeding-edge optimization window) by default.
  • Live application of governance is currently shadow (local_governance_live_mode="shadow") — it records what it would do without altering live orders yet. Same for live risk scalars (live_risk_scalars_mode="shadow").
Stage outputs are attached to every winner: walk_forward_audit, historical_audit_metrics, governance_policy, validation_evidence, then a promotion status — before the atomic ledger write.

Weak-train exception (specialists with a soft train but exceptional validation)

If train PF < 1.0 or train return < 0, the winner is still allowed only if validation is exceptional: val PF ≥ 1.5, val return ≥ 10%, val trades ≥ max(2×min, 50), val Sharpe ≥ 0.5, and val win-rate > 50%. Otherwise it is rejected to NO_TRADE.

Live re-check parity: the live loop re-applies is_valid_for_live(min_pf=1.05, min_return=5.0, max_dd=12.0, return_dd_ratio=1.0) using the same config keys, so a ledger winner that has drifted out of spec is re-blocked at the door rather than trusted blindly.

7 Live eligibility, sizing & supervision

A. Fail-closed startup (before any order)

  • live_artifact_drift_policy must be block.
  • MT5 account identity pinned & verified: expected_login / server / currency.
  • Connected equity ≥ live_min_account_equity in the right currency.
  • Manual kill switch flag not active; manual_new_entries_enabled true.
  • Winner ledger readable, non-empty, with tradeable winners.
  • No latched institutional-supervisor hard block.
  • Failure → --trade exits 2; paper mode still runs for diagnosis.

B. Per-bar decision (winners-only)

  • Loop triggers on a changed MT5 bar timestamp (live_loop_trigger_mode="bar").
  • Skip any TF with no promoted winner (cheap pre-filter).
  • Detect regime on the last closed bar (REGIME_LIVE.iloc[-2]); fail-closed if missing.
  • Look up the winner for the exact (TF, regime); skip if none / NO_TRADE / BLOCKED / PAPER_ONLY.
  • Re-apply the live quality gate (is_valid_for_live).
  • Generate the signal from the same closed bar; PROMOTE_SMALL carries a 0.5 risk multiplier.

C. Sizing, filters & protection (before order send)

  • Sizing: risk source = balance or equity (config: equity); risk_amount = equity × risk_per_trade_pct/100 (1.5%); loss-per-lot from MT5 order_calc_profit() at the stop; lot normalized to broker min/max/step; per-trade cap max_risk_pct (25%).
  • Spread quality: weak-edge rejection (min_edge_mult=1.25), spike block (spike_mult=3.0), soft penalty (penalty_start_mult=0.75).
  • Institutional supervisor (circuit breaker): hard blocks on daily/session/weekly loss, open drawdown, and total open-risk breakpoints; latch persisted across restarts.
  • Margin protection: entry block below level 60, recovery band from 55, panic forced-close at 50, stateful reopen only above 80; missing margin data fails closed when margin is in use.
  • Cycle-drift sentinel for consecutive local losses, slippage, and spread degradation.
  • Duplicate-position protection: sweep snapshot first, then a fresh broker-side position read immediately before send; same-symbol D1 + lower TF dual-trade controls.
Execution reality: signals are generated on closed candles and executed on the next actionable broker state, so live always has some inter-candle gap versus idealized backtest fills. The backtester models spread (conservative_max), commission, slippage on stop exits, and swap to keep that gap honest.

9 The bleeding-edge tradeoff & its mitigations

Optimizing on the newest 125k and validating on the older adjacent 50k maximizes live relevance (the model is tuned on the market context closest to the next trade) at the cost of a true forward holdout. The forward direction is unavailable by definition — the newest bar is the live edge. So overfitting-to-newest cannot be caught by forward OOS; it is contained by five other defenses:

  • Robustness / gap penalty — a winner must perform consistently across the newest 125k and the adjacent 50k, not just on one.
  • WFV sub-window persistence audit — the 50k validation slice is cut into 3 windows; all-negative or negative-min-score blocks promotion.
  • Historical stress audit — the oldest 50k flags strategies that blow up in a different regime; severe failure blocks.
  • Live cycle-drift & governance derating — real trade evidence pauses or derates a context as it decays.
  • 4-week retrain cadence — bounds how stale any deployed winner can become.
Rejected production shape: reserving the newest 15% as a hard clean holdout and selecting on it. That improves academic honesty but withholds the exact bars most predictive of the next live trades, making deployed strategies stale before use. It is retained only as the explicit research_clean_holdout mode for offline comparison.

10 Recommendations

Keep  Do not change the split direction or the promotion gate. The bleeding-edge geometry is implemented correctly, matches the documented contract, is locked by a versioned split contract, and is the right tradeoff for a decaying FX stack. The strict gate (only 1.6% of cells reach live) is the intended overfitting defense and should not be loosened without comparing regenerated artifacts and live outcome data.
Act  Periodically run research_clean_holdout as a shadow check. Bleeding-edge has no forward OOS. On a cadence (e.g. each retrain), run the same symbols in research_clean_holdout mode offline and compare which cells survive. Large divergence between the two flags cells that are likely overfit to the newest window — cheap insurance the production path can't give you.
Act  Decide on the "notify" retrain dependency before 2026-07-05. With production_retrain_mode="notify", all 38 live cells expire on 2026-07-05 and the book goes flat until a manual --optimize. Either commit to running the retrain on schedule, or switch to auto if unattended continuity is the goal. This is the single highest-impact operational risk to live continuity.
Watch  Governance and live-risk scalars are still in shadow. Stage 3 governance policies and live risk scalars are computed but not applied to live orders. That is the safe default, but it means the "best risk policy per winner" work is not yet shaping live sizing. Promote to active only after reviewing the shadow logs against live outcomes — then the system more fully realizes "best optimized strategy, best-managed, goes live."
Watch  Harden config-default parity (low priority). The live gate and validator read the same config keys, so they agree today. Their hard-coded fallback defaults differ (e.g. live max_dd default 35 vs validator 20) and would only diverge if a key were ever dropped from config.json. tests/test_config_json_integrity.py guards the keys; keep that test authoritative so the divergent defaults can never silently take effect.
Keep  Concentration on H4/H1 is expected, not a defect. Lower timeframes face proportionally larger spread/commission drag and shorter persistence, so fewer M5/M15 cells clear the gate. This is the cost model and validation doing their job, not a coverage gap to "fix".
