Live Startup Flow

1. Load configuration

Command entry is pm_main.py. It loads config.json, applies dataclass filtering, loads broker specs, and initializes PipelineConfig, PositionConfig, and MT5Config.

2. Connect to MT5

The system connects to the existing MT5 session or configured terminal. Live readiness validates account identity against expected_login, expected_server, and expected_currency.

3. Validate live readiness

pm_live_readiness.validate_live_readiness checks kill switch, account equity, risk bounds, storage floor, broker specs, ledger availability, expiry, artifact drift, promotion gate, symbol coverage, and explicit live regime-detector rows.

4. Load live-eligible ledger

PortfolioManager.get_live_eligible_configs returns only current, non-expired, artifact-compatible configs with at least one tradeable promoted regime cell.

5. Evaluate signals

LiveTrader evaluates only exact symbol/timeframe/regime winners. It computes live features from explicit detector rows, reads REGIME_LIVE, rejects missing regime cells, and skips all blocked or no-trade cells.

6. Execute with risk gates

Orders pass spread, margin, per-trade risk, min-lot hard-cap, symbol combined-risk, session/daily/weekly loss, open-drawdown, and supervisor checks before being sent.

Walk-Forward Validation Separation

Walk-forward validation is the adjacent validation surface before bleeding-edge optimization. The live layer uses currently validated promoted ledger cells; additional post-selection WFV hard blocking is controlled separately by the live-blocking policy.

SettingCurrent valueProduction interpretation
walk_forward_audit_enabled true WFV evidence may be produced during optimization/research.
walk_forward_promotion_policy observe_only WFV does not block promotion.
walk_forward_live_blocking_enabled false Even if a research config uses a block policy, production live does not block on WFV unless this is explicitly enabled.
walk_forward_do_not_displace_latest_surface true The newest selected surface remains the live candidate source; WFV should not consume the freshest live edge before execution.

Optimization And Validation Flow

  1. Symbol universe: config.json defines 100 symbols. The optimizer works through symbols using optimization_max_workers=4.
  2. Data fetch: historical M5 data is fetched with retry and deep backfill. If data remains insufficient, the symbol receives a NO_TRADE data-failure marker.
  3. Feature construction: indicators and regime features are generated per timeframe. Live depends on REGIME_LIVE, not a hindsight regime label. Promoted live cells require explicit regime-detector rows that reproduce the validation detector surface.
  4. Candidate search: strategy families are screened, tuned, and evaluated across the configured timeframes and regimes.
  5. Validation gates: candidates must satisfy trade count, profit factor, return, drawdown, robustness, holdout, and execution-cost checks. No fallback to best train is allowed when validation fails.
  6. Promotion status: validated cells are classified as PROMOTED, PROMOTE_SMALL, BLOCKED, PAPER_ONLY, or NO_TRADE.
  7. Atomic ledger write: each completed symbol is written atomically into pm_configs.json. A failed optimization produces a fail-closed no-trade marker rather than a weak winner.

Live Candidate Selection

Live trading uses a strict winners-only ladder. The current implementation refuses to trade if there is no exact winner for the current symbol, timeframe, and live regime. This is the key alignment point with the principle "no trade is better than an inaccurate strategy winner."

Residual Risks

  • No trading system can guarantee live profitability. This codebase can only improve selection discipline, execution controls, and fail-closed behavior.
  • The current live surface is limited to 14 promoted cells across 9 symbols until the optimizer finishes the remaining symbols.
  • A $20 account is highly sensitive to broker minimum lot size, spread, slippage, and margin changes. The min-lot hard cap helps, but small-account execution remains fragile.
  • Symbols that fail validation or data sufficiency will intentionally produce no trade, which may reduce activity but protects against inaccurate winners.
